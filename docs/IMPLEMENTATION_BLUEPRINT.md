# ReNe Implementation Blueprint

## 1. Purpose

This document is the working plan for implementing and evaluating ReNe: a learned manager for V2X cooperative freeway-merge agreements after acceptance. The project asks whether a compact learned policy can decide when to continue, cancel, or renegotiate an accepted agreement more effectively than fixed lifecycle rules, without weakening safety.

The core contribution is agreement lifecycle management. The project is not an end-to-end driving system: steering, acceleration, and lane-change execution remain under conventional controllers, and an independent deterministic safety shield can reject unsafe lifecycle actions.

## 2. Research question and hypothesis

### Research question

Can a learned post-acceptance agreement manager reduce failed-agreement duration and unnecessary cancellations compared with fixed rules while maintaining equivalent safety?

### Primary hypothesis

Under held-out combinations of traffic disturbances and V2X failures, the learned manager will reduce failed-agreement duration and unnecessary cancellation relative to fixed-threshold management, with no statistically detectable increase in collision or near-collision rate when all methods use the same safety shield.

### Valid outcomes

- Positive: learning improves one or more agreement-quality metrics without degrading safety.
- Mixed: learning helps only under certain disturbance or communication regimes.
- Negative: rules perform as well as or better than learning. This remains useful if the experiments identify when learning is unnecessary or brittle.

## 3. Scope

### Minimum viable project

- One freeway on-ramp topology.
- One learning-controlled agreement manager.
- Compact numerical observations rather than images or LiDAR.
- Three high-level actions: `CONTINUE`, `CANCEL`, and `RENEGOTIATE`.
- A small, discrete renegotiation menu.
- Three disturbance families: gap cut-in, unexpected braking, and V2X delay/loss.
- A deterministic feasibility checker and safety shield.
- Four non-learned baselines plus the learned manager.
- Reproducible training and held-out evaluation across multiple seeds.

### Explicitly out of scope for the MVP

- End-to-end steering or acceleration learning.
- Camera, LiDAR, or raw sensor observations.
- Free-form natural-language negotiation.
- Formal proof that the learned policy itself is safe.
- Real-vehicle deployment.
- SUMO/network co-simulation, recurrent policies, graph networks, and multi-agent learning unless the MVP is complete.

## 4. Available hardware and compute strategy

- CPU: AMD Ryzen 5 3600, 6 cores and 12 threads.
- GPU: NVIDIA GeForce RTX 3060 Ti, 8 GB VRAM.
- RAM: 32 GB.
- Operating system: Windows.

This is sufficient for the MVP. Start with four parallel environments and benchmark four, six, and eight. Because the policy is a small MLP and environment stepping is CPU-heavy, PPO may train as fast or faster on CPU than GPU. Measure both rather than assuming CUDA is preferable. Run full training seeds sequentially to avoid resource contention.

Cloud compute should be considered only for a large hyperparameter sweep, many simultaneous seeds, graph/recurrent models, sensor observations, or a strict deadline.

## 8. System architecture

```text
Scenario sampler
      |
      v
HighwayEnv merge simulation ---- V2X impairment model
      |                                  |
      +---------------+------------------+
                      v
       Lifecycle observation builder
                      |
                      v
       Agreement manager or baseline
       [continue | cancel | renegotiate]
                      |
                      v
       Feasibility check and safety shield
                      |
                      v
       Conventional trajectory controller
                      |
                      v
       State transition, reward, and metrics
```

The same scenario generator, low-level controller, feasibility checker, and safety shield must be used for every manager. Otherwise, differences cannot be attributed cleanly to lifecycle decision-making.

## 9. Agreement model

### Lifecycle states

Use an explicit state machine:

```text
PROPOSED -> ACCEPTED -> EXECUTING -> COMPLETED
                |           |
                |           +-> RENEGOTIATING -> EXECUTING
                |                                |
                +-------------------------------> CANCELED
```

Recommended enum values:

- `PROPOSED`
- `ACCEPTED`
- `EXECUTING`
- `RENEGOTIATING`
- `COMPLETED`
- `CANCELED`
- `FAILED`

The learning episode should begin with an accepted agreement or automatically construct and accept one before the learned manager receives control. Disturbances used for the main evaluation must occur after acceptance.

### Agreement record

Each agreement should store:

- Unique agreement and episode identifiers.
- Participant vehicle identifiers.
- Target gap identifier.
- Merge order.
- Planned merge time or time window.
- Acceptance time.
- Latest revision number.
- Current lifecycle state.
- Last manager action and action time.
- Feasibility status and reason code.
- Number of messages and renegotiation attempts.

### Renegotiation menu

Keep the initial menu small and deterministic:

- Delay the merge by a fixed time increment.
- Advance the merge by a fixed time increment.
- Select the next feasible gap.
- Swap merge order when the deterministic recipient accepts it.

If Stable-Baselines3 is used with one discrete action space, encode these as separate actions such as `RENEGOTIATE_DELAY`, `RENEGOTIATE_ADVANCE`, `RENEGOTIATE_NEXT_GAP`, and `RENEGOTIATE_SWAP`. For reporting, group them under `RENEGOTIATE`.

Limit renegotiation attempts per episode to prevent message loops. One or two attempts is enough for the MVP.

## 10. Observation design

Start with a flat, normalized vector suitable for an MLP.

### Physical features

- Ego speed and acceleration.
- Ramp vehicle speed and acceleration.
- Relative longitudinal positions and velocities.
- Current and predicted target-gap size.
- Distance to merge point.
- Traffic density.
- Minimum predicted time-to-collision.
- Minimum predicted time headway.

### Agreement features

- Current merge order.
- Encoded target gap.
- Time until planned merge.
- Agreement age.
- Execution progress.
- Revision count.
- Prior lifecycle action.
- Time since prior lifecycle decision.

### Communication features

- Age of the newest message.
- Current sampled delay.
- Rolling packet-loss estimate.
- Missing-message indicator.
- Stale-message indicator.
- Out-of-order-message indicator.

### Uncertainty features

- Difference between predicted and observed position.
- Difference between predicted and observed speed.
- Intent confidence score.
- Number of consecutive inconsistent observations.

Do not add recurrence initially. Use a short frame stack if one observation cannot distinguish a transient packet delay from a persistent intent change. Add a GRU only as a documented stretch experiment.

## 11. Action semantics

### Continue

Retain the current agreement for the next lifecycle interval. The shield may convert this to cancellation if the agreement is immediately unsafe.

### Cancel

Terminate coordination, notify participants, and switch to a conservative perception-only merge controller. Cancellation is not an episode failure by itself.

### Renegotiate

Generate one predefined counter-proposal. A deterministic recipient evaluates it using the same feasibility logic used by all managers. If accepted, increment the revision and update the agreement. If rejected, either retain the original agreement when still safe or cancel according to a declared rule.

Every proposed, applied, rejected, or overridden action must be logged separately.

## 12. Disturbance and V2X models

All disturbance parameters must be sampled from configuration files and written to the episode log.

### Traffic disturbances

- Gap cut-in: a non-connected vehicle enters the reserved target gap.
- Unexpected braking: a participant or nearby vehicle decelerates unexpectedly.
- Traffic shift: desired speed or local density changes after acceptance.
- Intent mismatch: actual acceleration differs from communicated intent.

### Communication disturbances

- Constant latency.
- Random latency drawn from a declared distribution.
- Bernoulli packet loss.
- Burst packet loss using a two-state model.
- Message reordering or stale delivery.

### Initial parameter grid

Use conservative values only as starting points and document all final values:

- Delay: 0, 100, 300, and 500 ms.
- Independent packet loss: 0%, 5%, 10%, and 20%.
- Braking severity: mild, moderate, and hard within simulator-safe bounds.
- Traffic density: low, medium, and high.
- Cut-in timing: early, middle, and late execution.

Do not run the full Cartesian product initially. Use a small training distribution and a targeted evaluation matrix.

## 13. Safety shield and feasibility checker

The safety shield must be independent of the learned policy and shared by all relevant baselines.

### Minimum checks

- Predicted minimum time-to-collision above a declared threshold.
- Predicted time headway above a declared threshold.
- Positive and sufficiently large target gap.
- Acceleration and deceleration within declared bounds.
- Merge completion before the usable ramp ends.
- Counter-proposal timing and gap are feasible for every participant.

### Override policy

- Unsafe `CONTINUE` becomes `CANCEL` or conservative fallback.
- Unsafe counter-proposal is rejected.
- Unsafe low-level action is replaced by the conventional safe controller.
- Every override records the requested action, applied action, triggering constraint, and state values.

The report must distinguish empirical safety under the tested conditions from formal safety guarantees.

## 14. Baselines

Implement and test baselines before training PPO.

### B0 Perception-only

No explicit V2X agreement. The conventional merge controller uses observable traffic only.

### B1 One-shot agreement

The accepted agreement remains active until completion unless the emergency safety fallback fires.

### B2 Rule-based cancellation

Cancel when one or more declared thresholds are crossed, such as minimum predicted gap, TTC, time headway, or message age.

### B3 Rule-based cancellation with heuristic renegotiation

Attempt one deterministic revision before canceling when an alternative gap or timing adjustment is feasible.

### B4 Learned lifecycle manager

Use PPO to select continue, cancel, or a specific bounded renegotiation action. Apply the same feasibility checker, shield, and low-level controller as B2 and B3.

B3 is essential. Without it, an improvement by B4 might result from merely having a renegotiation action rather than learning when to use it.

## 15. Reward design

Keep training reward separate from final evaluation metrics. A starting structure is:

```text
reward =
    + successful_merge_bonus
    - collision_penalty
    - near_collision_penalty
    - failed_agreement_time_penalty
    - unnecessary_cancellation_penalty
    - delay_penalty
    - discomfort_penalty
    - message_cost
    - shield_override_penalty
```

Guidelines:

- Use a large collision penalty, but never treat reward alone as a safety mechanism.
- Apply a small per-step cost while an agreement is known to be invalid.
- Penalize cancellation only when an oracle label says the original agreement would have remained feasible over the declared look-ahead horizon.
- Charge a small cost for lifecycle messages and renegotiation attempts.
- Avoid rewarding the policy directly for matching the rule-based baseline.
- Log every reward component separately.
- Run reward ablations if the final result depends strongly on one shaping term.

## 16. Ground-truth labels and metric definitions

Definitions must be frozen before the final experiment.

### Agreement invalidation time

The first simulation time at which the accepted agreement fails the declared feasibility test for a minimum persistence window. The persistence window prevents one noisy frame from labeling an agreement as failed.

### Failed-agreement duration

Time from agreement invalidation until cancellation, successful revision, safe recovery, or episode termination.

### Unnecessary cancellation

A cancellation is unnecessary if a privileged offline oracle, using true simulator state rather than delayed observations, determines that the original agreement would remain feasible over a fixed look-ahead horizon. Report the horizon and thresholds.

### Renegotiation success

A counter-proposal is successful if it is accepted, remains feasible, and leads to a completed merge without subsequent cancellation within the evaluation window.

### Near collision

Define using a fixed TTC and/or headway threshold. Report the threshold and whether TTC was ignored when vehicles were separating.

## 17. Metrics

### Safety

- Collision rate per episode.
- Near-collision rate.
- Minimum TTC.
- Minimum time headway.
- Safety-shield override count and reason.

### Agreement quality

- Agreement completion rate.
- Failed-agreement duration.
- Unnecessary-cancellation rate.
- Correct continuation rate.
- Renegotiation attempt, acceptance, and success rates.
- Repeated-renegotiation count.
- Lifecycle messages per successful merge.

### Efficiency and comfort

- Merge completion time.
- Ramp delay.
- Mainline speed disturbance.
- Throughput.
- Peak absolute acceleration.
- Peak jerk.
- Hard-braking count.

### Learning and system performance

- Training return and each reward component.
- Policy entropy and approximate KL divergence.
- Explained variance and value loss.
- Environment steps per second.
- Wall-clock training time.
- CPU, RAM, GPU, and VRAM utilization during representative runs.

## 18. PPO training plan

### Initial policy

- `MlpPolicy`.
- Two hidden layers of 128 units as the first trial.
- Four parallel environments initially.
- Frame stacking only if needed.
- Normalize observations using training data statistics.
- Keep reward scaling fixed after the pilot stage.

### Suggested tuning order

1. Verify the environment with random actions.
2. Verify that each rule-based baseline completes many episodes.
3. Train on a simplified curriculum with one disturbance.
4. Add randomized disturbance timing and severity.
5. Add communication impairment.
6. Tune learning rate, rollout length, batch size, entropy coefficient, and network size one at a time.
7. Freeze the configuration before final multi-seed training.

Do not tune against the final test set. Use separate training, validation, and final test scenario seeds.

### Compute benchmark

Benchmark these combinations for a short fixed number of steps:

- 1, 4, 6, and 8 environments.
- PPO on CPU.
- PPO on CUDA.

Select the configuration with the best stable wall-clock throughput. Stable-Baselines3 notes that PPO with an MLP is often CPU-oriented, so the RTX 3060 Ti is available but not automatically the fastest choice.

## 19. Data splits and experimental design

### Training split

Randomize within bounded ranges of traffic density, speeds, gap sizes, disturbance times, delays, and packet loss.

### Validation split

Use different seeds within the same ranges for model selection and reward/hyperparameter decisions.

### Final test split

Freeze the policy and evaluate on:

- New random seeds.
- Individual disturbances across severity levels.
- Held-out combinations, such as simultaneous cut-in and packet delay.
- At least one out-of-distribution but plausible severity setting.
- A no-disturbance control condition to measure unnecessary intervention.

### Fairness controls

- Use paired scenario seeds across methods.
- Use the same vehicle initial states and disturbances for every method.
- Use the same low-level controller and safety shield.
- Freeze all thresholds before final testing.
- Do not discard failed seeds or episodes.
- Report both aggregate and per-condition results.

## 20. Statistical analysis

- Use at least five independent training seeds if time permits; three is the minimum fallback.
- Target at least 1,000 test episodes per method and major condition when computationally feasible.
- Report means, medians, standard deviations, and bootstrap 95% confidence intervals.
- For paired continuous outcomes, analyze paired episode differences when the same scenarios are replayed.
- For collision and other proportions, report confidence intervals appropriate for binomial outcomes.
- Correct for multiple comparisons if many pairwise claims are tested.
- Report effect sizes, not only p-values.
- Do not interpret “not statistically significant” as proof that methods are equivalent. If claiming safety non-inferiority, define an acceptable margin before testing.

## 21. Logging and reproducibility

Every run should save:

- Run identifier and timestamp.
- Git commit hash.
- Full configuration snapshot.
- Python and package versions.
- Device selection.
- Training and scenario seeds.
- Environment and policy identifiers.
- Episode-level scenario parameters.
- Requested and applied lifecycle actions.
- Shield overrides and reason codes.
- Reward components.
- All final metrics.
- Model checkpoint and normalization statistics.

Use one row per episode for summary data and optionally one row per lifecycle decision for diagnostic traces. Never overwrite a completed run directory.

## 22. Testing requirements

### Unit tests

- Agreement state transitions reject invalid transitions.
- Counter-proposals increment revision numbers correctly.
- Delay and packet-loss models match configured behavior.
- Seeded reset reproduces initial conditions and disturbances.
- Metric calculations match hand-worked examples.
- Safety checks reject known unsafe states.
- Baseline thresholds behave correctly at boundary values.

### Integration tests

- Every manager can complete a short episode.
- The environment passes Gymnasium's environment checker.
- Vectorized environments can reset and step without cross-run state leakage.
- Training completes a small smoke run and saves a loadable model.
- Evaluation produces the expected schema and summary files.

### Scenario tests

- No disturbance: agreement usually remains valid.
- Obvious cut-in: unsafe continuation is blocked.
- Persistent stale messages: the configured rule baseline reacts as declared.
- Feasible alternative gap: heuristic renegotiation can succeed.
- No feasible alternative: renegotiation is rejected and fallback remains safe.

## 26. Required ablations

Run these only after the main comparison is complete:

- Learned manager without renegotiation.
- Learned manager without communication-quality features.
- Learned manager without uncertainty or frame history.
- Learned manager without the shield for diagnostic simulation only, never as the recommended system.
- Optional: smaller versus larger MLP.

The first two are the most important because they test whether renegotiation and communication context actually contribute to performance.

## 27. Risks and fallback decisions

### PPO does not learn reliably

- Simplify to continue/cancel first.
- Use curriculum training.
- Improve feature normalization and reward diagnostics.
- Keep B3 as a complete non-learning system.
- Report instability honestly if it remains.

### Unnecessary cancellation is ambiguous

- Freeze an offline oracle and look-ahead horizon.
- Add a persistence window.
- Report sensitivity to one alternate threshold.

### Simulation is too slow

- Disable rendering during training.
- Reduce logged step-level data during pilots.
- Benchmark worker counts.
- Reduce the evaluation grid while retaining paired seeds and core conditions.

### Scope expands too quickly

- Do not add SUMO, MARL, GRUs, graph models, or real datasets until the frozen MVP evaluation pipeline works.

## 28. Completion criteria

The project is complete when all of the following are true:

- A fresh environment can be installed from committed dependency files.
- The custom merge environment passes automated checks.
- Post-acceptance disturbances are reproducible from seeds.
- B0 through B4 run through one common evaluation interface.
- The safety shield and metric definitions have automated tests.
- At least three independent learned-policy seeds are evaluated; five is preferred.
- Paired held-out results include safety, agreement quality, efficiency, comfort, and communication metrics.
- Confidence intervals and limitations are reported.
- Final figures and tables are generated by scripts rather than manual editing.
- The README contains exact smoke-test, training, evaluation, and analysis commands.
- The report clearly distinguishes observed performance from formal safety guarantees.
- The repository contains no private data, credentials, or unnecessary large artifacts.
